# 终端图像

pane 里运行的程序可以向终端写入 Kitty 图形协议来绘制图像。`mux_server` 在字节到达模拟器之前就识别出这段序列，所以图像不会作为杂散字节落进网格；它被发布为一条带类型的通知，由客户端渲染。

## 支持的范围

传输的负载是 base64 编码的 PNG，程序需要多少个 `m=1` 分块就可以拆成多少块。服务端按到达顺序重组，收到最后一块时发布一张图像。发送时用 `a=T`；除删除之外的动作都按传输处理。

| 键 | 含义 |
| --- | --- |
| `a` | 动作。`d` 表示删除，其余都是传输。 |
| `f` | 格式。`100`（PNG）或省略，其余一律拒绝。 |
| `i` | 图像 id，用于后续替换或删除。 |
| `c`、`r` | 以终端单元格计的尺寸。 |
| `m` | 后面还有分块。 |
| `d` | 删除选择符。 |

`q` 会被接受但忽略：负载总是 base64。`x` 和 `y` 是裁剪偏移而不是单元格坐标，同样忽略——位置取自序列到达时的光标单元格。

序列里的其余内容一律忽略而不是拒绝。无法识别的键不应该让程序付出任何代价；格式错误的序列会被记录并丢弃，不影响周围的文本。

## 滚动

图像锚定在实时视口上。向上翻进历史时图像会隐藏，直到视口回到底部。

这是有意为之。图像不属于服务端保存的滚动历史——那是一张单元格网格——所以它没有对应的历史行。把它按同样的屏幕位置画在更早的文本上，等于把它放到了它从未出现过的地方。

## 改变尺寸

一次放置会保留它拿到的单元格坐标。改变 pane 尺寸会让文本围绕它重排；图像不移动，也不缩放。希望图像跟随尺寸变化的程序自己重绘即可，这和它对待其余在意的输出并无不同。

## 上限

每个 pane 最多保留 256 张图像、256 MB 已解码帧，单次放置每边最多 4096 个单元格。超出上限的帧会被拒绝，已经在屏幕上的图像原样保留：一串本身合法的帧不应该能挤掉程序已经画出的内容，也不应该耗尽浏览器进程。

## 可用性

两个客户端走同一条路径。桌面应用和 WebAssembly 客户端渲染的是同一条通知，因为画出图像的就是同一份代码。
